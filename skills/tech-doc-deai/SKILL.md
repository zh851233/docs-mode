# 技术文档去 AI 味

对技术类文书执行去 AI 味改造。**方向是"像工程师写的"，不是"像口语说的"**：更准确、更简洁、更具体、术语统一。严禁口语化（的话/这块儿/说白了）。

## 何时使用

- 用户明确要求去除 AI 味 / AI 痕迹 / AI 腔。
- docs 模式创作完成后主动询问，用户确认后触发。

## 工作流

### 1. 精准打击，不大改

- 只改命中高危句式库的句子，其余一字不动。
- 一次只改一个方向：第一轮句式改造 → 第二轮红线自检 → 第三轮通读终检。
- 不全文重写、不大段替换、不一次改太多（会把 AI 味改回来）。
- **数字、版本号、参数、命令原文保留，绝不改动**；术语不因改造而变乱。

### 2. 按高危句式库逐句改造（技术文档版示例）

| AI 特征句式 | 改造方法 | 示例 |
|-----------|---------|------|
| `从……角度/维度看` | 直接陈述，或"在……方面" | "从系统架构角度看，模块A负责…" → "模块A负责…" |
| `通过……等途径，在……等方面` | 拆短句，补具体数值 | "通过缓存、索引等途径提升性能" → "引入缓存与索引后，查询性能提升约40%" |
| `首先……其次……最后` | 用编号列表 | "首先校验权限，其次加载配置" → "1. 校验权限 2. 加载配置" |
| `不仅……而且……` | 拆两个分句 | "不仅支持X，而且支持Y" → "支持X，也支持Y" |
| `面对这个挑战` | "针对上述问题"或直接陈述 | |
| `发挥着……作用` | "承担……职责"/"用于……" | "发挥着数据清洗的作用" → "承担数据清洗职责" |
| `提供了有力支撑` | "支撑了……"/"为……提供基础" | |
| `综上所述` | 直接给结论句 | "综上所述，方案可行" → "结论：方案可行" |
| `是……的体现/证明/保障` | 改动宾结构 | "是系统可维护性的保障" → "保证了系统可维护性" |
| `全方位、多层次、复合型` 排比 | 具体列举 | "全方位安全防护" → "覆盖权限、配置、审计三层的安全防护" |
| 长并列 `把……把……把……` | 拆分或表格化 | |

**高频 AI 词汇替换**：赋能/抓手→删除或具体化；助力→支持/提升；打造→构建/实现；显著/高效/强大/无缝/一站式/闭环→给具体数值或手段，不给空洞形容词。

**删冗余填充词**：`可以`、`进行`、`相关`、`一定`、`较为`、`来说`、`的话`、`方面`——能删则删（"用于数据清洗、转换与归一化"而非"可以用于对数据进行清洗、转换以及归一化处理"）。

### 3. 技术风格红线自检（交付前逐项过）

- [ ] 语气中性：无口语词、无感叹号、无情感化修辞
- [ ] 术语统一：专有名词全文一致；首次出现给全称+缩写
- [ ] 数据可验证：性能/规模给具体数值与单位，不用"大幅/明显"
- [ ] 命令可执行：命令块标注环境与前置条件
- [ ] 简洁：短句优先，能表格不用排比
- [ ] 破折号 `——` 全篇≤2处，解释用括号或逗号
- [ ] 无空话段：删"具有重要意义""值得关注"类句子
- [ ] 引号规范：正文全部使用中文引号“ ”，无英文双引号 "（代码块内保持原样）

### 4. 交付

- 报告改了多少处、改了哪些类型（如"命中句式8处：转场句3、排比2、总结句3"）。
- 交付前对照原文：信息量未减、术语未乱、数字未变；正文引号全为中文“ ”。

## 原则

- 只改命中句，不多改；每次修改有针对性。
- 技术文档的"AI 味"主要来自：模板转场、空洞总结、排比堆砌、冗余填充——改造这三类即可，不必逐句动刀。
- 可调用 humanizer-zh / remove-ai-flavor / stop-slop 复核，但主改造以本技能为准（它们是通用向，本技能是技术文档专用向）。
