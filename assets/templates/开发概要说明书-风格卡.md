# 内置风格卡：系统开发概要说明书

> 用途：无用户模板时的默认模板之一（用户传入模板时以用户模板为准）。

## 语言规范

- **语气**：正式、技术性、面向设计与开发人员；比使用说明书更偏"实现"，但仍是概要级，不贴大段代码。
- **人称**：第三人称 + 无主语客观叙述（"系统采用……""该平台以……"）。
- **句式**：长复合句可适度使用，先总述后展开；技术名词直接用英文专名（React、Dijkstra、H3 等）。
- **术语**：全篇术语统一；首次出现可给出中文全称+英文（如"位置服务（Location Based Service，LBS）"）。
- **数字**：数据要真实具体（规模、百分比、版本号、参数值），允许引用公开行业数据并注明口径。
- **引号**：默认中文引号“ ”，结合上下文——文档主体为英文时用英文引号 " "，中文语境引用英文原文可保留英文引号；代码块内保持原样。

## 格式规范

- **标题编号**：阿拉伯数字"1. / 1.1. / 1.1.1."（软著主流）或中文"一、/（一）"；一份文档内保持一致。
- **表格**：功能描述表三列（模块名称 | 功能要点 | 关键需求）；环境表三列（项目 | 类别 | 详情）；数据资产表四列（资产文件 | 内容 | 规模 | 质量等级）。
- **图片**：架构图、流程图、ER 图、用例图、数据字典图；图注"图N 图名"在图下方；正文须先引用。
- **分点**：并列要点用"1. 2. 3."；编写目的用"（1）（2）（3）"。
- **算法/公式**：关键算法可给出公式与阈值，用规范排版。

## 思路特征

- **编排顺序**：背景与目标 → 总体设计（功能全景→环境→数据）→ 架构（框架图→模块分解）→ 核心功能实现 → 出错处理与维护。即"是什么→怎么设计→怎么实现→怎么兜底"。
- **每模块讲解套路**：一段功能叙述（该模块做什么、关键规则、交互链路）→ 图佐证。
- **技术点讲解套路**：功能（做什么）→ 实现原理（怎么做，可列分点）→ 应用场景 → 意义。四段式，层次固定。
- **论证方式**：架构选择给理由（"确保……可维护性和可扩展性，降低耦合度"）；技术方案给数据。
- **过渡**：章节首段常以"本章将详细阐述……""该图展示了……"引入。

## 避免事项

- 不放完整源代码，只讲设计与实现思路；接口用模块/函数级描述而非代码。
- 不写操作界面细节（那是使用说明书的内容）。
- 架构图、数据图必须与真实系统一致，不画"示意图"。
- 项目背景不编造市场数据；引用数据注明来源。
- 不出现与配套文档（使用说明书）冲突的术语、模块名、版本号；两份文档共用同一张功能描述表。
- 无法核实的信息（提出者/开发者名称、硬件配置等）用「XX（待补充）」占位并明确告知用户。

## 结构红线（对照自检）

1. 引言含：项目背景（含系统名称/提出者/开发者/用户/架构五要素）、编写目的、参考资料；
2. 总体设计含：功能描述表 + 运行环境（硬件/软件）+ 数据设计（无数据库时如实改写）；
3. 系统架构含：整体架构图 + 逐模块设计；
4. 出错处理（软著申报版必须有）：出错信息/补救措施/软件维护；
5. 所有图编号连续、正文有引用；数据与版本号来自真实项目；引号风格与文档语言一致。
