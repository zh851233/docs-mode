# 内置风格卡：需求规格说明书

> 用途：无用户模板时的默认模板之一（用户传入模板时以用户模板为准）。

## 语言规范

- **语气**：中性、精确、无歧义；需求句用"系统应/必须/将……"（shall 风格）。
- **人称**：无主语或"系统/用户/管理员"角色名。
- **句式**：短句 + 祈使陈述；每条需求一个句子，避免"和/或"模糊表达。
- **术语**：术语表统一定义；同一概念全文同词。
- **数字**：一切指标量化（时间、容量、并发、精度），禁止"高效/快速/大量"。
- **引号**：默认中文引号“ ”，结合上下文（英文文档/英文原文引用用英文引号）。

## 格式规范

- **标题编号**：阿拉伯数字"1. / 1.1."；功能项编号 FR-01/FR-02，业务规则 BR-01。
- **表格**：用户角色表、术语表、数据字典、验收清单——表格是主力表达。
- **强调**：**加粗** 用于优先级、关键字（"必须/不得"）；注意用 `> ⚠️` 引用块。
- **列表**：需求条目用编号列表；同一功能的多个输入输出用嵌套列表。

## 思路特征

- **编排顺序**：引言 → 总体描述（定位/用户/环境）→ 功能需求（按模块）→ 非功能 → 数据 → 界面 → 验收。
- **功能项套路**：编号与名称 → 优先级 → 输入/处理/输出 → 业务规则 → 异常处理。
- **论证方式**：不论证，只定义；每条需求独立成立、可单独测试。

## 避免事项

- 不写"用户应该能方便地……"类主观描述；改为具体行为与约束。
- 不把实现细节写进需求（"用 Redis 缓存"是设计不是需求）；如必须则标注为设计约束。
- 不使用模糊词：尽快、尽可能、等等、大概。
- 需求之间不矛盾、不重叠；同一行为只定义一次。
- 不编造用户角色、数据来源、验收指标——无法核实的信息用占位并说明。

## 结构红线（对照自检）

1. 功能需求全部编号（FR-xx）且与验收清单一一对应；
2. 非功能需求全部量化；
3. 术语表覆盖全文缩写；
4. 异常处理覆盖主要失败场景；
5. 引号风格与文档语言一致。
